# macOS Wi-Fi switching and authorization research

**Research date:** 2026-10-26
**Question:** Can Seamless WiFi switch between already-saved secured networks without asking for a Keychain or administrator password on each switch?
**Scope:** Apple primary sources only (developer.apple.com docs and technotes, Apple DTS forum replies, support.apple.com, and man pages shipped with macOS). Where Apple does not document something, this file says so and labels any inference.

## Short answers

1. **Why the admin prompt?** The prompt text **“Seamless WiFi wants to use the ‘System’ keychain”** is a Keychain access-control prompt, not a CoreWLAN association prompt. The saved Wi-Fi password lives in the file-based System keychain; an app that is not in the item's ACL is prompted. Apple DTS says modern macOS partitions file-based keychain items so that *the user must confirm cross-context access* and that there is no way to make an item silently accessible to other apps. See [Why the prompt appears](#why-the-prompt-appears).
2. **Can installer or first-run authorization grant durable per-app access?** Not through any Apple-documented mechanism found. Authorization Services and `SMAppService` grant *privileges*, not Keychain ACL entries. The documented durable grant is a user-approved ACL change (**Always Allow** or Keychain Access → Access Control), and Apple DTS says even that ACL change requires user approval. See [Installer and first-run authorization](#installer-and-first-run-authorization).
3. **Does signing identity matter?** Yes. File-based Keychain ACLs track the app by its code-signing designated requirement (DR). Ad-hoc signed code has a DR tied to that exact build, so trust does not survive rebuilds. A stable identity (self-signed for local tests, Developer ID for release) is required for a grant to persist across updates, but it is necessary, not sufficient. See [Code-signing identity continuity](#code-signing-identity-continuity).
4. **Supported alternatives?** CoreWLAN is the only supported macOS API for association; `NEHotspotConfigurationManager` is iOS only. All variants need either a password the app holds or admin authorization. See [Supported alternatives](#supported-alternatives-for-wi-fi-association).

## Why the prompt appears

- [Access Control Lists](https://developer.apple.com/documentation/security/access-control-lists): each protected file-based keychain item has an ACL of operations and trusted apps. If the calling app is not trusted, "the system prompts the user for confirmation. The user may choose to Deny, Allow, or Always Allow the access. In the latter case, the system adds the app to the list of trusted apps for that entry, enabling the app to gain access in the future without prompting the user again."
- [TN3137: On Mac keychain APIs and implementations](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains): in a user context the file-based keychain search list contains the per-user login keychain and a single **System** keychain. The file-based keychain uses ACLs (`SecAccess`); the data protection keychain uses access groups. Programs that read *existing* file-based items must target the file-based keychain, so the data protection keychain is not an option for reading the system's saved Wi-Fi item.
- [Apple DTS (Quinn), forum thread 131428, Apr 2020](https://developer.apple.com/forums/thread/131428), about a third-party app reading a Wi-Fi password and getting a username/password prompt: "we added partitioning to the traditional file-based keychain. This means there's no way to create a keychain item that can be silently accessed by other apps, or the system, or vice versa. You may be able to modifying the ACL for the item to prevent future access, but the act of modifying the ACL will itself require user approval." A follow-up reply says there is no equivalent to `SecKeychainUnlock` for this case "because the entire goal of this keychain partitioning features is for the user to confirm the cross-security-context access."
- [Apple DTS (Quinn), forum thread 759976](https://developer.apple.com/forums/thread/759976): `/Library/Keychains/System.keychain` is writable only by root.
- [Add certificates to a keychain](https://support.apple.com/guide/keychain-access/add-certificates-to-a-keychain-kyca2431/mac): Apple documents that working with the System keychain may ask for an administrator name and password.

**Inference (not stated verbatim by Apple):** the administrator prompt appears because the item is in the System keychain, which is shared system state, rather than the login keychain where a user password or click would suffice. Apple does not document the exact string “wants to use the ‘System’ keychain”. Given the code path (`.user` then `.system`), the prompt most likely comes from `CWKeychainFindWiFiPassword(.system, ...)`.

Apple's [`CWKeychainFindWiFiPassword`](https://developer.apple.com/documentation/corewlan/cwkeychainfindwifipassword%28_%3A_%3A_%3A%29) page (macOS 10.9+) documents only: "Finds and returns, by reference, the password for the SSID and keychain domain you specify." It says nothing about prompts, ACLs, or authorization.

## Two separate authorization dialogs

1. **Keychain access:** the saved network password's ACL, as above. A Keychain prompt can request administrator credentials when the item is in the System keychain.
2. **Network association authorization:** [`CWInterface.associate(to:password:)`](https://developer.apple.com/documentation/corewlan/cwinterface/associate%28to%3Apassword%3A%29) (macOS 10.7+): "password … Required for association to WEP, WPA Personal, and WPA2 Personal networks." and "This operation may require an administrator password." The enterprise variant [`associate(toEnterpriseNetwork:identity:username:password:)`](https://developer.apple.com/documentation/corewlan/cwinterface/associate%28toenterprisenetwork:identity:username:password:) carries the same warning. [`requireAdministratorForAssociation`](https://developer.apple.com/documentation/corewlan/cwconfiguration/requireadministratorforassociation) is documented as "Require an administrator password to change networks." A configuration value of `false` does not prove association never prompts.

Resolving Keychain authorization does not prove association authorization is absent. These are separate operations and must be tested separately.

## Installer and first-run authorization

- [Authorization Services](https://developer.apple.com/documentation/security/authorization-services) is documented for "software installers that install privileged tools or require access to restricted areas of the operating system". It grants *rights* through the Security Server. The pages reviewed do not describe any right that edits a Keychain item's ACL or adds an app to a trusted-app list. Rights obtained in an `AuthorizationRef` are not documented as a durable, per-app, per-item grant. [`AuthorizationCopyRights`](https://developer.apple.com/documentation/security/authorizationcopyrights%28_%3A_%3A_%3A_%3A_%3A%29) can pass credentials in the environment to avoid a dialog, but that requires the app to already hold an administrator password, which it should not.
- Programmatic ACL editing exists ([`SecAccessCreate`](https://developer.apple.com/documentation/security/secaccesscreate%28_%3A_%3A_%3A%29), [`SecTrustedApplicationCreateFromPath`](https://developer.apple.com/documentation/security/sectrustedapplicationcreatefrompath%28_%3A_%3A%29), [`SecKeychainItemSetAccess`](https://developer.apple.com/documentation/security/seckeychainitemsetaccess%28_%3A_%3A%29)) but all three are **deprecated since macOS 10.10 ("SecKeychain is deprecated")**. Per Apple DTS above, changing an ACL itself needs user approval, and [`SecAccessCreate`](https://developer.apple.com/documentation/security/secaccesscreate%28_%3A_%3A_%3A%29) says the owner entry (the one that can change the ACL) has an empty trusted list "so the user is always prompted for permission if someone tries to change the access instance."
- The `security` man page that ships with macOS documents `set-generic-password-partition-list`: "The 'partition list' is an extra parameter in the ACL which limits access to the item based on an application's code signature. You must present the keychain's password to change a partition list." **Inference, untested:** adding an app to the Access Control list may not be sufficient if the item's partition list excludes the app's team; a scripted install-time change would need the System keychain's password. Apple documents no supported way for an installer to obtain it silently. Do not script this.
- [`SMAppService`](https://developer.apple.com/documentation/servicemanagement/smappservice) / [helper updating guide](https://developer.apple.com/documentation/servicemanagement/updating-helper-executables-from-earlier-versions-of-macos): "Launch daemons require authentication by the user because the user is authorizing a system level-process." This is a one-time administrator approval for a root helper. Apple does not document that a root helper reading the Wi-Fi item avoids Keychain prompts or that it removes the association authorization. [`SMJobBless`](https://developer.apple.com/documentation/servicemanagement/smjobbless%28_%3A_%3A_%3A_%3A%29) is deprecated (macOS 13) in favor of `SMAppService`.
- TN3137 notes root daemons must target the file-based keychain, and Quinn (thread 759976) notes a root daemon *can* write to the System keychain. This shows a root helper is architecturally able to use the System keychain; it is not evidence that reads of the Wi-Fi item are prompt-free.

**Conclusion:** installer or first-run flows can request admin approval once, but Apple documents no mechanism that converts that approval into a durable per-app Keychain grant. The supported durable grant is the user's own ACL decision (Always Allow, or Access Control), which Apple's own forum guidance says requires user approval.

## Code-signing identity continuity

- [Code Signing Guide](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html): "The creating application is automatically trusted with its item, and determines the access policy using code signing requirements." The designated requirement (DR) tells the system how to identify code; "Any two pieces of code that have (and successfully verify against) the same DR are considered to be the same code. This allows a code signer to publish a new version of an app that is treated as the same app." The guide also says "Self-signed identities and homemade certificate authorities (CA) work by default for this case [keychain/parental controls] … they may be useful during development or for test purposes" but not for Gatekeeper.
- [TN3127: Inside Code Signing: Requirements](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements): "Ad hoc signed code, called Sign to Run Locally by Xcode, has a DR but it's tied to that specific version of the code … If you tweak the code and run it again, macOS repeats that prompt." It lists "the keychain presents unexpected authorization alerts when you deploy your app through a new channel, like TestFlight" as a symptom of changing identity. Default DRs combine signer (`anchor apple generic` plus Team ID for Apple-issued identities) and `identifier`.
- **Project facts:** the installed app was inspected with `codesign -dv` and is **ad-hoc signed** (`Signature=adhoc`, no Team Identifier). A trust grant made to one ad-hoc build is not expected to carry to the next. The development Mac (macOS 26.1) has zero valid code-signing identities, so a Developer ID A/B test cannot run from this checkout. A locally created self-signed identity could test continuity but cannot be distributed.
- Keep a **stable bundle identifier and signing identity** across releases. Do not mix Apple Development, Developer ID, and TestFlight/App Store builds when testing a grant.
- The in-memory password cache now stores the credential immediately after Keychain returns it, even if association fails. It is empty after restart. It reduces repeat Keychain reads in one process; it does not make the first read prompt-free and does not affect association authorization.

## Implementation and validation notes

- `NetworkSwitcher` reads a saved password with `CWKeychainFindWiFiPassword` (`.user`, then `.system`) and passes it to `CWInterface.associate(to:password:)`.
- Manual row taps and Automatic mode call the same `AppModel.switchTo` path, so an automatic switch triggers the same Keychain and association operations as a manual one.
- Prior diagnostics tried association with `password: nil`; CoreWLAN returned `com.apple.wifi.apple80211API.error`, code `-3900`. This is consistent with the documented password requirement but is not proof for every macOS release or profile.
- In one local diagnostic run, the probe could not read SSID names (`SSID: unavailable`; scan results `<hidden>`), so a successful automatic switch was **not** demonstrated. Absence of a prompt in Automatic mode is not evidence that switching worked.
- A reported System keychain prompt requested administrator credentials. This is distinct from any authorization prompt that might occur during association.

## Import-at-install assessment

An installer cannot silently extract Wi-Fi passwords from saved profiles with the documented CoreWLAN profile API ([`CWNetworkProfile`](https://developer.apple.com/documentation/corewlan/cwnetworkprofile) exposes SSID and security type, not the password). A first-run import that enumerates SSIDs and calls `CWKeychainFindWiFiPassword` would move the same System keychain prompt to setup (once per item), create a second stored copy, and not address association authorization. Do not implement credential import.

## Recommended diagnostic and fix sequence

1. **Keep macOS as the credential store.** In Keychain Access, select the **System** keychain, find the **AirPort network password** item for the SSID, open **Access Control**, and add the installed Seamless WiFi app (per [Apple's steps](https://support.apple.com/en-gb/guide/mac-help/kychn002/mac)); or choose **Always Allow** if the dialog offers it. Expect an administrator prompt for this change. Do not choose "Allow all applications". If the prompt persists after adding the app, suspect the partition list (see above) and record it as a finding; do not script around it.
2. **Use a stable signing identity first.** Sign every test build with one stable self-signed identity (local) or the Developer ID identity (release), with a constant bundle identifier, *before* granting access. Then test: relaunch, rebuild with the same identity, and update. Ad-hoc builds will keep re-prompting.
3. **Instrument the switch stages.** Log timestamps around scan, Keychain lookup start/end, and association start/end, excluding passwords and optionally SSIDs, to attribute each prompt to its stage.
4. **Test association authorization separately.** After the Keychain prompt is gone, check whether `associate(to:password:)` raises its own admin prompt. Prototype the preferred-network-order alternative and an `SMAppService` helper only if it does.
5. **Re-test automatic and manual behavior separately.** Grant Location Services so SSIDs are visible, verify automatic mode invokes the switcher, verify target association and connectivity, switch back, and repeat without restarting the app. Repeat after app restart and after an update to see which authorization persists.

## Recommendation

Do not add import-at-install, and do not expect installer or first-run authorization to remove the System keychain prompt: Apple documents no mechanism for it, and Apple DTS says cross-context keychain access is meant to need user confirmation. The least invasive path is a stable signing identity plus a one-time, user-approved ACL grant for the existing System keychain item. If an association prompt remains after that, evaluate the preferred-network-order approach or a helper as a second step; neither is a confirmed fix.
